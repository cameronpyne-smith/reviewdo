# <img width="48" height="48" alt="Reviewdo" src="assets/reviewdo-bot.png" align="absmiddle" /> Reviewdo

Automated pull request reviews, posted by a GitHub App, generated by a local
Ollama model. No webhooks, no inbound connections, no repo checkout.

## How it works

A single Go binary with no third-party dependencies polls GitHub every minute
using a GitHub App installation token. Polling uses conditional requests, so
a repository with no new activity costs nothing against the rate limit. For
each configured repository it:

1. Lists open pull requests.
2. Scans new issue comments for `@reviewdo-bot review`.
3. Reviews a PR when it is newly opened (or leaves draft) by a person, when
   a trusted member comments `@reviewdo-bot review`, or when the `reviewdo`
   label is added. PRs opened by bots such as Dependabot are reviewed only
   on request.
   Requests by comment are reviewed first, then labels, then newly opened
   PRs, oldest first; every repository is rescanned between reviews so a
   new request never waits behind the backlog.
4. Fetches the diff and runs the checks that need no model: every
   declaration the diff adds, changes or removes with where the repository
   uses that name; each changed file against its counterparts under sibling
   directories (environment overlays, sibling apps), naming the keys most
   of them set that this file lacks; the dependencies declared by the
   nearest manifests with their versions; paths and links written in added
   lines that do not exist at the head commit; keys removed from
   configuration, workflow or translation files that the repository still
   uses; names in added strings and values that occur nowhere else but
   have a differently spelled near match; and added lines that name a
   sibling environment of the file they are in. These go into the prompt
   as facts. The model then reads
   the repository at the PR's head commit through read-only tools, and
   posts the result as a review: a
   verdict, a one-line summary, a findings list with each finding's
   severity and title linked to its inline comment, and a collapsed table
   of what changed.

With `clone_dir` set, each configured repository is cloned there on first
use. Before each review the PR is re-read from GitHub, so a head or base
that moved while it was queued is picked up and a PR closed in the meantime
is skipped, and its head and base commits are fetched by SHA, so a base
branch deleted after a stacked merge still works. `reviewdo clone` clones
them all up front so no first review waits on a clone. The model reads files
with `git show <sha>:<path>`, so nothing is ever checked out and the working
tree can be used normally. A file over 24 KB is not returned whole: the model
gets its outline and the regions the PR changes with surrounding lines, and
reads anything else by line range, so a few large files cannot fill the
context window. Without `clone_dir`, reviews use the diff alone.

Large pull requests are reviewed in parts of related files, each with full
tool access, then merged. With `review.units` on, a deep pass runs first,
with its own time budget (`review.units_time`): it takes each changed
function in the code files (tests, examples and documentation excluded),
shown whole with line numbers, in small groups, and asks the model in a
single call with no tools to state each function's contract and then find
one concrete sequence of events that breaks it. Functions are ranked by how
many of their lines do something that can go wrong (I/O, concurrency,
timing, error handling, parsing, loops), so a pull request too big for
`units_time` still gets its riskiest functions examined. One draw misses what
another finds, so `review.units_draws` asks again, every function once
before any twice, with the functions regrouped each draw so each sits with
different neighbours, and merges the answers, noting under each finding how
many draws produced it. A draw can ask a different question or run on a
different model, since a second model's mistakes are less likely to repeat
the first one's than its own second attempt is. The question is
deliberately bare: on the benchmark a reviewer framing, a list of cases to
check, an instruction to report only what the code shows, the pull request
description, changed-line markers or a list of callers each turned the
answer into "no break found" on a function with a planted bug. The noise
the bare question produces is what triage and verification remove. The
whole-PR pass then runs with its usual share of `time_budget`, and
verification of both passes' findings gets the rest; findings it has no
time for are posted marked `[Unverified]`. It is off by default. When the repository has instruction files, a
separate pass with no tools checks every added line against them and
reports each breach with the rule quoted; a quote that does not appear in
the instructions is discarded. A triage pass drops findings that say nothing
concrete: reassurance, requests to "please verify", generic advice. Every
remaining finding is re-checked by a separate, sceptical verification pass
against the files before it is posted, highest severity first; rejected
findings are dropped and overstated ones downgraded. The verifier states
what each verdict rests on: a finding that rests on how a browser, framework
or library behaves must name the exact rule and is never posted above minor,
and a rejection that rests on such knowledge rather than on the repository
keeps the finding and posts it at minor. When the time reserve
runs out, the findings not yet checked are still posted, marked
`[Unverified]`, and the verdict is capped at "Merge with care".

Re-reviews after a previous review only cover the commits added since then,
unless history was rewritten or the base branch was merged in, in which case
the whole PR is reviewed again.

On first run with no state file, PRs that are already open are not reviewed
automatically. Use a comment or the label to review them. Set
`auto_review` to `false` to never review a PR just because it was opened:
only a comment or the label starts a review. PRs first seen while it is off
are treated like those existing PRs, so turning it back on does not review
them.

## Security posture

- Outbound HTTPS to `api.github.com` and `github.com` (git fetch) and HTTP to
  `127.0.0.1:11434` only. Nothing listens.
- The model's tools are `read_file`, `list_dir`, `search`, `search_base`,
  `definition`, `references` and `outline`, all served by `git show`,
  `git ls-tree` and `git grep` at the PR head commit or the base branch.
  The symbol tools are pattern matches, not a language server, so no
  build, restore or analysis of repository code ever runs. Nothing from the repository is ever executed:
  no hooks, no builds, no tests, no submodules.
- Git runs with system and global config disabled and no credential helper.
  The installation token is passed per command through the environment and is
  never written to the clone.
- The app has `Pull requests: read & write` and `Contents: read` only.
- The private key is passed to the service by systemd `LoadCredential`, readable
  by root only on disk. It is never in this repo or in dotfiles.
- The service runs as a `DynamicUser` with a locked-down systemd sandbox
  (`deploy/reviewdo.service`).
- PR content is untrusted. Every pass that sees the title, description,
  code or file contents is told they are untrusted and never to follow
  instructions found in them. The model only produces JSON that becomes
  review text; its tools are read-only, paths are confined to the
  repository, and it executes nothing.
- Review requests via comment are honoured from anyone who can comment on a
  private repository, since access there already implies membership, and
  only from `OWNER`, `MEMBER` or `COLLABORATOR` accounts on a public one.
  The app cannot see organisation membership, so members of a private
  organisation appear as `CONTRIBUTOR`.

## Install

```
./deploy/install.sh
sudo install -m 0600 -o root -g root ~/.config/reviewdo/private-key.pem /etc/reviewdo/private-key.pem
sudoedit /etc/reviewdo/config.json
sudo systemctl enable --now reviewdo
journalctl -fu reviewdo
```

## Commands

```
reviewdo -config config.json check                       # verify key, access, model
reviewdo -config config.json clone                       # clone every configured repo now
reviewdo -config config.json pulls owner/repo            # list open PRs
reviewdo -config config.json review owner/repo#12        # dry run, prints the review
reviewdo -config config.json review -post owner/repo#12  # post it
reviewdo -config config.json review -model m -think false owner/repo#12
reviewdo -config config.json facts [-units] owner/repo#12  # print the code-side checks for a PR, no model
reviewdo -config config.json run                         # poll loop (default)
```

### Benchmark

`reviewdo bench` measures reviews against Copilot's, using pull requests whose
Copilot comments the authors already replied to. Every reply says whether the
finding was real, so the labels come for free. The data lives in `bench/`
(gitignored, it quotes your code) and the review runs at the commit Copilot
reviewed, against the PR's base at the time, so the same bugs are present.

```
reviewdo -config config.json bench mine -authors me,colleague [-org o]   # collect reviewed PRs into pool/
reviewdo -config config.json bench label [-since 2026-07-01] [-only r#N]  # label findings into golden/
reviewdo -config config.json bench dedupe [-since 2026-07-01] [-only r#N] # fold repeated findings so each problem scores once
reviewdo -config config.json bench export -out dir -since 2025-08-26      # every PR with reviews, threads, commits and diffs
reviewdo bench propose -since 2026-07-01 -n 10 -write                      # pick a smoke set
reviewdo -config config.json bench run -label base [-model m -think t]     # review and score the set
reviewdo -config config.json bench run -label probe -only r#N -units f.rs:39 # deep pass only, on the functions at these lines
reviewdo -config config.json bench score -label base                       # rescore without reviewing
# scoring judges every finding the review produced, including any the comment cap would not post
reviewdo bench report -label tweak -against base                           # compare two runs
```

Labelling: a thread with no reply is `unclear`; a reply that references a
commit is `valid`; otherwise the model reads the reply and decides `valid`,
`invalid` or `unclear`. Verdicts can be fixed by hand in the golden file
with `"locked": true`, and reviewdo's own findings can be added there with
`"source": "reviewdo"` once checked, so later runs are scored against them
too. Copilot often repeats one finding at every place it applies ("same as
above"); `bench dedupe` asks the model to group those and marks each repeat
with `duplicate_of`, so a group counts as one finding, found when any member
is. Locked findings are left as they are.

`bench run` clones into `bench/clones`, reviews each PR in the set
sequentially with the configured budget (`-budget` overrides it), skips PRs
already in `runs/<label>/`, then scores. Scoring pairs each golden finding
with a review comment using the local model as a judge, cross-checked by a
same-file-within-five-lines match. The report gives recall on valid
findings, how many rejected Copilot findings were repeated, time and tool
calls per PR, and the comments that matched nothing, which
`runs/<label>/triage.md` lists for checking by hand. There is no pass/fail
gate; compare runs.

## Review guidance

Three layers are added to every prompt, in this order: global instructions
from the config, per-repo instructions from the config, and instruction files
owned by the repository itself. The repository files are the same ones Copilot
uses: `.github/copilot-instructions.md`, and every
`.github/instructions/*.instructions.md` whose `applyTo` glob matches a file
changed by the PR. They are read from the base branch, not the PR head, so a
PR cannot rewrite the rules it is reviewed under.

## Config

See `deploy/config.example.json`. Fields:

| field | default | notes |
|---|---|---|
| `app_id`, `installation_id` | | from the GitHub App settings |
| `private_key_path` | `$CREDENTIALS_DIRECTORY/private-key` | set explicitly when not under systemd |
| `state_path` | `$STATE_DIRECTORY/state.json` | set explicitly when not under systemd |
| `clone_dir` | unset | where repositories are cloned; unset means diff-only reviews |
| `poll_interval` | `60s` | |
| `label` | `reviewdo` | label that triggers a review; removed afterwards |
| `auto_review` | `true` | review PRs when they are opened; `false` reviews only on `@reviewdo-bot review` or the label |
| `repos[].name` | | `owner/repo`, or `owner/*` for every repository the installation can reach; archived repositories are skipped and the list is refreshed every poll |
| `instructions`, `instructions_file` | | global review guidance for every repo, inline or from a file |
| `repos[].instructions`, `repos[].instructions_file` | | guidance for that repo only |
| `exclude_repos` | | `owner/repo` names never polled, useful with `owner/*`; `review owner/repo#N` still works on them |
| `ollama.model` | | required |
| `ollama.num_ctx` | `32768` | context window requested from Ollama |
| `ollama.num_predict` | `12288` | output tokens per model round, thinking included; stops runaway deliberation |
| `ollama.think` | unset | `true`/`false`, or an effort level such as `"low"` for models that support one |
| `review.max_diff_bytes` | `3 × num_ctx` | diff budget; remaining files are listed by name |
| `review.max_comments` | `15` | inline comments per review, highest severity first |
| `review.part_bytes` | `40000` | diff bytes per review part; larger PRs are split into parts. Reduced automatically so that the diff and the review guidance together take at most 35% of the context window |
| `review.part_time` | `2m` | minimum time for each part, so a large PR is read properly even when it overruns the budget |
| `review.triage` | `true` | one fast model call before verification that drops findings which say nothing concrete (reassurance, "please verify", generic advice) and sets each finding's severity from fixed definitions |
| `review.verify` | `true` | verify every finding with a second pass before posting, highest severity first |
| `review.units` | `false` | the deep pass over changed functions, run before the whole-PR pass |
| `review.units_time` | `time_budget` | time budget for the deep pass, on top of `time_budget` |
| `review.units_draws` | `1` | times the deep pass runs over the changed functions, regrouped each time; findings from different draws within 5 lines merge and carry how many draws found them. A list instead of a count sets each draw: `{"question": "contract", "inputs" or "exits", "temperature": 0.7, "model": "gemma4:31b", "think": false}`, each field optional; `model` runs that draw on another Ollama model, with `think` as for `ollama.think` |
| `review.time_budget` | `5m` | target duration for one review; parts and verification are cut short to fit |
| `review.timeout` | `3 × time_budget` | hard deadline, after which the review is abandoned |
| `review.max_output_tokens` | `48000` | total output tokens per review before the final answer is forced |
| `review.max_tool_calls` | `200` | file reads, listings and searches the model may make per review |
| `review.ignore` | lockfiles, vendor, minified, generated | glob on basename or path, `dir/` for prefixes |
